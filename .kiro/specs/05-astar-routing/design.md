# Spec 05 design

## A* in one paragraph

A* explores ports in order of `f = g + h`. `g` is the real cost from the start so far. `h` is a guess of the cost still
to go. Dijkstra is A* with `h = 0`: it is always correct but explores blindly in all directions. A good `h` steers
the search toward the goal. A bad `h` (one that overestimates) can make A* return a worse route without any error.

## Why our heuristic is safe (the argument to include in the write-up)

Let `d(a,b)` be the haversine (straight-line over the globe) distance.

1. **Every lane is at least as long as the straight line.** The graph builder rejects any edge with `distance_km < d(from,to)` (R1.2).
2. **Any path from n to the goal is at least `d(n, goal)` long.** Sum of lane lengths >= sum of straight lines >= `d(n, goal)` by the triangle inequality.
3. **`minCostPerKm`** is `min over edges of (edgeCost / distance_km)`. So every edge costs at least `distance_km * minCostPerKm`.
4. Therefore any real path from n costs at least `d(n, goal) * minCostPerKm = h(n)`. The heuristic never overestimates: it is **admissible**.
5. It is also **consistent** (`h(n) <= cost(n,m) + h(m)`), because `d(n,goal) <= d(n,m) + d(m,goal)` and `d(n,m) * minCostPerKm <= cost(n,m)`.
   Consistency means each port is finalized once, so a simple closed set is correct.

Edge case: if `minCostPerKm` is 0 (for example a risk-only objective with a zero-risk lane), `h = 0` and A* behaves like Dijkstra. That is valid, just not faster.
`minCostPerKm` is computed on the **active** graph after disruptions are removed, which can only make it larger (tighter) and still safe.

## Cost normalization

`T_hat = transit_days / max_transit_days`, likewise F and R. Without normalization, dollars would swamp days and risk
and the weights would be meaningless. Max values come from the graph being searched.

## Modules in `packages/core/src/routing/`

- `haversine.js` (done, tested)
- `graph.js`: `buildGraph(ports, edges)` validates (R1.2), exposes `neighbors(code)`.
- `cost.js`: `makeCostFunction(graph, weights)`, `OBJECTIVES`.
- `heap.js`: small binary min-heap (no dependency).
- `astar.js`: `findRoute(graph, from, to, weights)`.
- `dijkstra.js`: reference implementation used by tests only (kept in `test/helpers`).
- `explain.js`: builds the plain-language explanation.

## Data

`supabase/seed/ports.json` and `edges.json` (about 20 ports). `distance_km` is generated by a script as
`ceil(haversine * 1.3)` to represent sea lanes being longer than straight lines; the generator is in `scripts/` and the label stays `illustrative`.
Times and costs are invented for the demo and marked so.

## Tests (`packages/core/test/routing.test.js`)

Direct lane; multiple routes; each objective picks a different route on a crafted graph; disrupted node and edge (via spec 06 overlay);
no route; start equals goal; unknown port; invalid weights; edge shorter than straight line rejected; determinism of ties;
**property test**: on 500 random graphs, A* total cost equals Dijkstra total cost for random weights.

## Risks

- Real freight data is not available free. The demo says "illustrative" everywhere and does not claim quotes.
- Map library choice: Leaflet with OpenStreetMap tiles needs attribution; a plain SVG map is the fallback.
